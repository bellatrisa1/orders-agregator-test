# Orders Aggregator

Сервис синхронизации заказов и расчёта ежедневной статистики по клиентам.
Загружает заказы из внешнего API, принимает обновления через вебхуки и агрегирует
оплаченные заказы по календарным дням в часовом поясе клиента.

## Возможности

- Полная синхронизация заказов с курсорной пагинацией и повторными запросами при временных ошибках API.
- Обработка вебхуков с проверкой версии заказа по `updatedAt`.
- Расчёт суммы до скидок, фактической оплаты и скидки в целых копейках.
- Группировка по IANA-таймзоне клиента с учётом переходов на летнее время.
- Совместимость с заказами без полей скидки и прежним значением `total`.

## Технологии

Node.js 20.11+, TypeScript, Fastify, PostgreSQL 16, Zod, Vitest, Prettier.

## Архитектура

HTTP-маршруты передают запросы сервисам, сервисы реализуют бизнес-логику,
репозитории отвечают за доступ к PostgreSQL. Внешний API подключается через
интерфейс `OrdersApi`; зависимости собираются в `createContainer(db, api)`.

```text
src/
  clients/        HTTP-клиент внешнего API: пагинация, ограничение частоты, повторы
  repositories/   Хранение заказов, часовых поясов и результатов синхронизации
  services/       Нормализация заказов, синхронизация, расчёт статистики
  routes/         HTTP-маршруты и валидация запросов
  utils/          Денежные преобразования и календарные даты
  app.ts          Fastify-приложение и обработка ошибок
  container.ts    Сборка зависимостей
  db.ts           Подключение к PostgreSQL и миграции
  server.ts       Запуск и завершение работы сервера
migrations/       SQL-миграции
scripts/          Инициализация тестовой БД
test/             Модульные и интеграционные тесты
```

## Запуск

Требуются Node.js 20.11+ и Docker с Docker Compose. Команды выполняются из корня
проекта. Стандартные порты: `3000` — сервис, `4000` — внешний API, `5432` — PostgreSQL.

Загрузите предоставленный с заданием образ для своей архитектуры:

```bash
# Apple Silicon / ARM64
docker load -i ../orders-mock-arm64.tar.gz

# Для x86_64 используйте orders-mock-amd64.tar.gz
```

Установите зависимости и подготовьте окружение:

```bash
npm ci
cp .env.example .env

set -a
source .env
set +a

docker compose up -d
docker compose exec -T postgres pg_isready -U postgres -d orders
```

После готовности PostgreSQL примените миграции и запустите сервис:

```bash
npm run migrate
npm run dev
```

Для запуска без отслеживания изменений используется `npm start`.
Переменные из `.env` необходимо экспортировать в каждом новом терминале:
npm-скрипты не загружают этот файл автоматически.

### Переменные окружения

| Переменная          | Назначение                | Значение из примера                                       |
| ------------------- | ------------------------- | --------------------------------------------------------- |
| `DATABASE_URL`      | Подключение к основной БД | `postgres://postgres:postgres@localhost:5432/orders`      |
| `TEST_DATABASE_URL` | Отдельная БД для тестов   | `postgres://postgres:postgres@localhost:5432/orders_test` |
| `ORDERS_API_URL`    | Адрес внешнего API        | `http://localhost:4000`                                   |
| `PORT`              | Порт сервиса              | `3000`                                                    |

При изменении портов публикации Docker соответствующие адреса в `.env` должны
быть согласованы с `docker-compose.yml`. Значение `PORT` определяет порт приложения.

## API

| Метод  | Маршрут                                                     | Назначение                         |
| ------ | ----------------------------------------------------------- | ---------------------------------- |
| `GET`  | `/health`                                                   | Проверка доступности сервиса       |
| `POST` | `/sync`                                                     | Синхронизация всех страниц заказов |
| `POST` | `/webhooks/order`                                           | Применение обновления заказа       |
| `GET`  | `/customers/:id/daily-totals?from=YYYY-MM-DD&to=YYYY-MM-DD` | Ежедневная статистика клиента      |

### Синхронизация и вебхуки

`POST /sync` отвечает после завершения обхода страниц:

```bash
curl --fail-with-body -X POST http://localhost:3000/sync
```

Ответ содержит счётчики `pages`, `received`, `applied`, `stale`, `invalid`.
Вебхуки используют ту же нормализацию, что и синхронизация. Повторная или
устаревшая версия получает `200 { "result": "stale" }`.

Штатная отправка вебхуков из образа задания:

```bash
docker compose run --rm orders-api webhooks --target http://host.docker.internal:3000/webhooks/order
```

### Ежедневная статистика

```bash
curl --fail-with-body \
  'http://localhost:3000/customers/c_7/daily-totals?from=2026-03-27&to=2026-03-31'
```

Пример записи ответа:

```json
{
  "date": "2026-03-27",
  "total": 24736,
  "gross": 24736,
  "discount": 4880.49,
  "net": 19855.51
}
```

- `gross` — сумма оплаченных заказов до скидок.
- `net` — фактически оплаченная сумма.
- `discount` — разница между `gross` и `net`.
- `total` — прежнее поле ответа; равно `gross`.

Диапазон включает обе границы. Дни без оплаченных заказов возвращаются с нулевыми
суммами. Учитывается текущий статус `paid`; дата определяется по `createdAt`
в часовом поясе клиента. `updatedAt` используется для сравнения версий.

### Правила расчёта

Деньги хранятся и суммируются в целых копейках; ответ возвращается в рублях.
Доли копейки во входных суммах отбрасываются. Небезопасные и некорректные значения
отклоняются, переполнение дневного итога проверяется.

Корректный `amountPaid`, включая ноль, имеет приоритет над `discountPercent`.
Если оба поля отсутствуют, `net = gross`. Если передан только процент,
`net` рассчитывается от суммы в копейках с округлением до ближайшей копейки,
половина вверх. Процент принимается числом или десятичной числовой строкой
в диапазоне от 0 до 100. Присутствующее невалидное поле не игнорируется.
В рамках модели скидок фактическая оплата не может превышать сумму заказа.

Миграция `002_amount_paid.sql` добавляет фактически оплаченную сумму. У старых
записей она первоначально равна сумме до скидки: восстановление ранее утраченных
скидок требует отдельных данных. Повторная версия с тем же `updatedAt` не применяется.

## Внешний API

- `GET /orders?cursor=<string>&limit=<1..100>` → `{ items: Order[], nextCursor: string | null }`.
- `GET /customers/:id` → `{ id, timezone }`, где `timezone` — IANA-идентификатор.
- Вебхук передаёт заказ в теле `POST /webhooks/order`.

```ts
type Order = {
  id: string;
  customerId: string;
  amount: number | string;
  discountPercent?: number | string;
  amountPaid?: number | string;
  status: "pending" | "paid" | "refunded";
  createdAt: string;
  updatedAt: string;
};
```

Числовые строки подтверждены ответами предоставленного API. Временные метки
хранятся в UTC; строки без указателя зоны интерпретируются как UTC.

## Проверки

Интеграционные тесты используют отдельную `orders_test` и очищают её таблицы.
Внешний API в тестах заменён `FakeApi`.

```bash
npm run typecheck
npm test
npm run format:check
```

Форматирование проекта:

```bash
npm run format
```
