# Решение и проверка

## Что исправлено

- Рубли переводятся через десятичное представление и BigInt в целые копейки:
  `0.29 → 29`, `1.15 → 115`, `10.999 → 1099`. Доли копейки, как раньше, отбрасываются.
  Некорректные, отрицательные, бесконечные и небезопасные суммы отклоняются;
  безопасный диапазон проверяется также при чтении БД и суммировании дней.
- Общая нормализация синхронизации и вебхуков учитывает скидки. `amountPaid`,
  включая ноль, имеет приоритет; без обоих новых полей `net = gross`.
  Процент проверяется даже при наличии оплаты. Его несовпадение с фактической
  оплатой не приводит к пересчёту amountPaid.
- При наличии только процента net вычисляется от целых копеек с точной
  рациональной арифметикой BigInt и округлением до ближайшей копейки, половина вверх.
  Это принятое правило совместимости: внешний контракт не описывает округление.
- Миграция `002_amount_paid.sql` добавляет `amount_paid_kop`, старые записи
  заполняет из `amount_kop`. `001_init.sql` не менялась. Хранится денежный результат,
  а не избыточный процент. Предполагается модель скидки: `0 <= amountPaid <= amount`.
- Локальная дата определяется через Intl по IANA-зоне на момент `createdAt`,
  а не по текущему смещению. `updatedAt` остаётся версией, не временем оплаты.
- Ответ: `date, total, gross, discount, net`, где `total = gross`,
  `discount = gross - net`. Суммирование и вычитание выполняются в копейках.
  Учитывается текущий статус paid; пустые дни остаются нулевыми.
- Сигнатура `createContainer(db, api)` и интерфейс `OrdersApi` сохранены.
  Новые зависимости не устанавливались.

## Причина расхождений на данных c_7

`GET /customers/c_7` внешнего API вернул `Europe/Berlin`.
29 марта 2026 в 01:00 UTC смещение меняется с +01:00 на +02:00.
Локальные сутки 29 марта имеют 23 часа. Старая реализация брала смещение
на момент запроса; на дату проверки в ноябре это +01:00. Поэтому часть заказов
после перехода попадала на предыдущий день. Результат зависел от сезона запроса.

На тех же конечных данных воспроизведена старая группировка со смещением +60 минут:

| Дата       | Старый total (+01:00) | Исправленный total |
| ---------- | --------------------: | -----------------: |
| 2026-03-27 |              24736.00 |           24736.00 |
| 2026-03-28 |              58233.00 |           58233.00 |
| 2026-03-29 |              43964.00 |           34658.00 |
| 2026-03-30 |              52201.00 |           59684.00 |
| 2026-03-31 |              44064.00 |           35401.00 |

Конкретные оплаченные заказы, меняющие день при старом алгоритме:

| Заказ   | createdAt UTC            | Старый день | Правильный день | gross, руб. |
| ------- | ------------------------ | ----------- | --------------- | ----------: |
| o_02357 | 2026-03-29T22:40:08.000Z | 2026-03-29  | 2026-03-30      |     9306.00 |
| o_02448 | 2026-03-30T22:40:44.000Z | 2026-03-30  | 2026-03-31      |     1823.00 |
| o_02545 | 2026-03-31T22:15:49.000Z | 2026-03-31  | 2026-04-01      |     5487.00 |
| o_02547 | 2026-03-31T22:40:06.000Z | 2026-03-31  | 2026-04-01      |     4999.00 |

Таким образом, кодом и фактическими заказами подтверждено расхождение по части
дней при использовании текущего зимнего смещения; первые два дня совпадают.
Это воспроизведение старого алгоритма на данных API задания, а не сравнение
с платёжным отчётом: сам отчёт не предоставлен. Историческое время выполнения
запроса аналитиками неизвестно. Общий дефект потери копейки тоже воспроизведён
тестами, но gross заказов c_7 в данном диапазоне целочисленный, поэтому объяснять
им наблюдаемые здесь расхождения оснований нет.

Группировка по созданию сохранена согласно текущему контракту; paidAt в нём нет.
Поздний updatedAt не переносит заказ на дату оплаты или обновления.

## result.json и проверки

Ответ сохранён непосредственно curl, без составления данных вручную:

```bash
curl --fail-with-body --silent --show-error 'http://127.0.0.1:3000/customers/c_7/daily-totals?from=2026-03-27&to=2026-03-31' -o result.json
```

JSON разобран и проверен: пять дат 27–31 марта по порядку, обязательные поля,
конечные денежные значения с точностью до копейки, total === gross,
discount в копейках равен gross минус net. Независимая SQL-агрегация PostgreSQL
по `created_at AT TIME ZONE 'Europe/Berlin'` подтвердила gross и net всех 5 строк.

- `npm run typecheck` — успешно.
- `TEST_DATABASE_URL=postgres://postgres:postgres@127.0.0.1:55432/orders_test npm test`
  — 8 файлов, 39/39 тестов успешно на реальном PostgreSQL 16 из Compose.
  Очистка только orders_test отдельно разрешена пользователем; orders_final не очищалась.
- Тесты охватывают денежные границы, строки процентов из реального API,
  приоритет и ноль amountPaid, только процент, старый формат, несколько заказов,
  статусы, обновления/повторы/старые события, DST, границы диапазона,
  независимость от текущего времени и миграцию старых записей с откатом транзакции.

## Допущения и ограничения

- Для старой БД миграция не восстанавливает утраченные скидки. Событие с тем же
  updatedAt игнорируется: для обогащения понадобится отдельное решение.
- Сохранена прежняя схема get → save; атомарная защита от гонки одновременных
  sync/webhook остаётся задачей на будущее. В данном сценарии они выполнялись последовательно.
- Внешний источник — предоставленный образ orders-mock:3, не платёжная система.
  Сверка с её отчётом не выполнялась, соответствие производственному API не заявляется.
- Временные диагностические снимки/логи сохранены в /private/tmp, в репозиторий
  не добавлялись. Состав дней и изменения зафиксированы выше.
- Для локального запуска используется orders_final на порту 55432, для тестов —
  orders_test на том же порту. .env локальный; при запуске в другом окружении
  нужно согласовать порты Compose и переменные, а не подключаться к чужой БД.
- Два пустых незапущенных контейнера первой попытки удалены с разрешения пользователя,
  без удаления томов. Контейнеры других проектов не изменялись.
- Для работы использован Codex: анализ, правки и тесты. Результат проверен
  исполняемыми тестами, ответами предоставленного API и независимым SQL-запросом.
- Работодателю ничего не отправлялось, репозиторий не публиковался.
